# Проверка среды, даты и постоянные коды

Версия пакета 0.4.0, контракт 1.1; формат конфигурации остаётся version=1.
Старые источники с корректной aware as_of и собственными постоянными code работают.
Новые поля ответа добавлены без изменения интерфейса FinanceAdapter и старых позиций Report.

## Перед установкой

```sh
python3 preflight.py environment
python3 preflight.py environment --network
```

Первая команда использует только стандартную библиотеку и не требует установленного MCP.
Проверяет Python >=3.11, venv/ensurepip и запись во временный каталог. Она явно выводит,
что пакеты, сеть и сервер PostgreSQL ещё не проверены. Флаг --network отдельно делает
короткий запрос к индексу PyPI, без установки пакетов. Сбой сети может требовать разрешения
инструмента/настройки DNS или прокси; не переписывайте комплект ради обхода среды.

После установки `pip install '.[files,postgres]'` для полного прогона:

```sh
.venv/bin/python -m finance_mcp.diagnostics environment --packages
.venv/bin/python -m finance_mcp.diagnostics environment --packages --postgres-bin /usr/lib/postgresql/18/bin
```

PG_BINDIR — каталог **серверных** initdb/pg_ctl/postgres, а не только psql. Проверяется
существование и реальный запуск всех трёх --version с таймаутом. Отсутствующие библиотеки
тоже дают отказ до длинного suite. PostgreSQL-клиентский адаптер сам сервер не устанавливает:
эти программы нужны для локальной тестовой репетиции. Для неё нужны Linux/WSL и не-root.
При отдельно распакованном сервере используйте --postgres-share <каталог с postgres.bki>,
а библиотеки передайте через локальный LD_LIBRARY_PATH. Никакие системные изменения
или сетевые установки doctor не выполняет. Пропуски not_checked не являются успехом.

Для временного runtime без системного сервиса администратор может скачать Ubuntu/Debian
серверный пакет и библиотеки, распаковать их dpkg-deb -x в отдельный каталог, проверить
--version, затем задать FINANCE_MCP_TEST_PG_BINDIR и FINANCE_MCP_TEST_PG_SHAREDIR для тестов.
Точные имена пакетов/библиотек зависят от ОС; агент выясняет их локально. Не используйте
клиентскую боевую БД для проверки установки сервера или тестового сидирования.

## Короткая диагностика stdio

```sh
.venv/bin/python -m finance_mcp.diagnostics stdio --timeout 15
.venv/bin/python -m finance_mcp.diagnostics stdio --config /absolute/client/config.json --timeout 15
```

Выход 0: состоялись initialize/list_tools, найден набор шести инструментов. Это не
сверка сумм и не регистрация в UI клиента. Выход 1: JSON указывает этап и timeout/process_error.
Выход 2: неверные параметры/запрет запуска процесса. Время ожидания ограничено 1–60 секунд;
watchdog завершает собственный процесс и его потомков. На Linux/WSL проверена очистка
группы, на Windows используется taskkill /T (отдельная Windows-приёмка ещё не проводилась).

Проба не вызывает финансовые отчёты, не печатает паспорт, DSN или сырые stderr. Timeout
сам по себе не доказывает ошибку адаптера или ограничения sandbox. Отдельно выполните
--check и сравните тот же пакет в окружении с разрешённым запуском процессов/stdio,
если политика среды это допускает. Требующие разрешений команды выполняет администратор
или основной ход; агент передаёт точную команду и фиксирует вмешательство в акте.

## Даты: состояние данных и получение

| Поле Report / reports | Значение |
|---|---|
| as_of | Подтверждённая дата состояния учёта с TZ или null |
| received_at | Когда получили отчёт/экспорт, aware ISO datetime или null для старого источника |
| as_of_status | confirmed (по умолчанию для старого честного as_of) или unknown |
| source_time_raw | Исходный текст даты без домысленного TZ, необязателен |

Для unknown обязательны as_of=null и aware received_at. Нельзя вставить время получения
в as_of и оставить unknown. При confirmed обе известные даты должны иметь TZ, дата состояния
не может быть позже получения. Отсутствие received_at старого источника не означает,
что время получения известно. --check предупреждает о неизвестном состоянии учёта.

В CSV пустая as_of = null. Добавьте новые необязательные поля в **явную полную карту columns**
реестра reports; то же для XLSX и разрешённых колонок PG-представления. Пример:
examples/lipa/csv-dates.json, reports-dates.csv. Для PG nullable as_of — timestamptz,
received_at — timestamptz, as_of_status/source_time_raw — text. Код колонок/состав старого
представления не нужно менять до перехода на новые поля.

Если старый экспорт ошибочно записывал время получения в as_of (как исходная репетиция
Полки), это не подтверждённая дата. При миграции перенесите его в received_at, задайте
unknown/as_of=null и сохраните исходный текст. Часовой пояс не угадывается, наивные
даты не превращаются в UTC автоматически. Методика и дата согласуются в акте.

## Реестр устойчивых кодов

Входной rows.code должен быть стабильным ID, не хэшем/номером текущего названия.
Если источник его даёт и клиент подтвердил смысл, прежний прямой code остаётся допустим.
Если нужна карта названий/ID, задайте article_registry: "articles.json" в JSON источника.
Готовый пример — examples/lipa/csv-registry.json и articles.json.

```json
{
  "version": 1, "client_id": "client_b",
  "entries": [{
    "kind": "pnl", "code": "revenue_services", "source_ids": ["erp:17"],
    "labels": ["Работы", "Ремонт"], "approved_by": "владелец, дата согласования"
  }]
}
```

Сопоставление ограничено клиентом и видом отчёта. При наличии source_id (необязательная
колонка rows, добавляется в columns) ищется только он; неизвестный ID не заменяется
похожим названием. Заполненный code обязан совпадать с каноническим. Без source_id
используется явный code; если code пустой — единственный согласованный алиас label.
Неизвестность, неоднозначность, конфликт и несогласованное название дают отказ.

При переименовании оставьте прежний code и добавьте новый label в labels, сохраняя
старый алиас и source_ids. Алиасы и подтверждение выбирает владелец, агент не создаёт
коды автоматически. Реестр только читается, исходные файлы/БД не меняются.

```sh
.venv/bin/python -m finance_mcp.registry articles.json --client-id client_b
.venv/bin/python -m finance_mcp.registry articles-new.json --client-id client_b --previous articles.json
```

Проверка обновления запрещает удаление старых кодов, ID и алиасов, переназначение ID
другому коду. Храните прежний реестр вместе с актом/отпечатками и проверяйте до каждого
обновления; сам runtime не имеет доступа к прежним файлам и не подтверждает историю
без --previous. Изменение экономического смысла требует отдельного согласованного
нового кода и повторной сверки, а не переиспользования старого.
